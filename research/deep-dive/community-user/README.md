# community and user research: the people, not the parts

> thesis: every capability table in the corpus describes what keeberia can
> do. this folder asks the harder question: what do the people who actually
> make keyboards want, and what would make them trust generated copper and
> generated plastic over doing it themselves. opinions are not evidence:
> recurring pain points across build logs are.

or simply put: read what makers complain about before deciding what to
build next.

## sources to mine (phase 16, dispatch when anne says go)

- geekhack and deskthority build logs and help threads
- r/mechanicalkeyboards and r/ergomechkeyboards build posts and struggle
  threads
- discord communities where findable and quotable
- qmk/zmk docs trouble spots (where the docs themselves warn about
  common mistakes)

## deliverable

an evidence-backed user-need list: recurring struggles with counts and
source threads, mapped to which keeberia engine (if any) already answers
them. not opinions, not marketing personas.
